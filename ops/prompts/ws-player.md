SPEC: `ws-player` — build the lesson player: the full-screen flow from START to the lesson-complete screens.

Read: CLAUDE.md, docs/DESIGN-SYSTEM.md §2.2 (lesson screen), §2.3 (lesson-complete sequence, out-of-hearts, quit dialog), §6, §8 (sound, motion, accessibility); docs/ARCHITECTURE.md §3.2 (lesson lifecycle), §10.1–10.2 (a guest's first lesson; outbox replay), §12 (offline); docs/LEARNING-ENGINE.md §5 (re-queue), §7.3 (client/server grading); `apps/web/lib/challenge-registry.ts` (READ-ONLY renderer contract: the player owns the flow, renderers own one challenge), `apps/web/lib/api-client.ts` + `apps/web/lib/app-services.tsx` (READ-ONLY: `useApi`, `useHome`, `queryKeys`), `packages/session-engine` (`gradeResponse`), `packages/contracts` (CreateSessionResponse, SessionEventRequest, CompleteSessionRequest, SessionResult), `packages/ui` (ProgressBar, FeedbackBar, Button3D, Modal, BottomSheet, ConfettiBurst, Character, StatPill).

URL CONTRACT (other workstreams link here): `/lesson?course=<courseId>&kind=<lesson|practice|letters|unit_review>&level=<levelId>` (`level` omitted for practice). The route lives in `apps/web/app/lesson/` (outside the (app) chrome: full screen, max width ~640px, no nav). Leaving returns to `/learn` (or `/letters` for letters sessions, `/practice` for practice).

DELIVER
1. An XState v5 machine (`apps/web/lib/lesson/`) for the session: loading (createSession) → answering → checking (grade locally with `gradeResponse`, lexicon from the session content where available) → feedback (correct/wrong; wrong costs a heart via `sessionEvent` unless practice; wrong challenges are re-queued at the end, Duolingo-style) → … → completing (`completeSession`) → complete screens; plus out-of-hearts (modal: practice to earn one, or quit), quit confirmation ("Wait, don't go! …"), expired/`gone` handling, and resume after reload (snapshot the machine + answers in IndexedDB via `idb`, keyed by sessionId). Pure logic stays framework-free and unit-tested.
2. An offline-tolerant outbox in IndexedDB for `sessionEvent` and `completeSession` calls: FIFO, idempotent by (sessionId, attemptSeq) / sessionId, replayed on reconnect and on next app start; the complete screens render from the server's `SessionResult` when online, or an optimistic local summary when offline, then reconcile.
3. The UI (`apps/web/components/lesson/`): top bar (close X, `ProgressBar` with the streak glow after 3+ correct in a row, hearts), the renderer from `rendererFor(type)`, the footer (SKIP + CHECK, CHECK grey until the renderer reports a response), `FeedbackBar` (correct: "Nice!" style message; wrong: "Correct solution:" + `closestSolution`, report flag that opens a small report sheet posting `createReport`), CONTINUE; keyboard: Enter = CHECK/CONTINUE, Escape = quit dialog; sounds (short correct/wrong/complete effects you synthesize or generate as tiny files in `apps/web/public/sounds/`, respecting `settings.sound`) via Howler with preloading of all session audio before challenge 1; character lip-sync through `ChallengeAudio.mouthOpen()` from the envelope JSON.
4. Lesson-complete sequence: XP / accuracy / time cards with count-up → streak extended screen (flame, days) → daily goal screen (when just met) → CONTINUE back to the path; confetti (reduced-motion aware). Invalidate `queryKeys.home` and `queryKeys.path` after completion.
5. Tests: machine unit tests (every transition incl. re-queue order, hearts, out-of-hearts, resume, gone), outbox tests (fake IndexedDB, e.g. `fake-indexeddb`), dom tests for the footer/feedback/complete screens, and Playwright specs in `e2e/lesson/` that play the fixture's first lesson `u01-s0` (`/lesson?course=fixture&kind=lesson&level=u01-s0`, signed in with the `guestPage` fixture from `e2e/fixtures`) through the real API: answer everything correctly → complete screens → home XP updated; a wrong answer → heart lost + re-queued; reload mid-lesson resumes; offline completion (Playwright `context.setOffline`) is replayed when back online. If the real renderers from ws-renderers are not on main yet, drive the challenges through a test-only renderer map injected via a React context you own (never modify the read-only registry), and keep the e2e specs data-testid based so they keep working once real renderers land.
